# 커밋 스킬

변경사항을 읽고, 리뷰하기 쉬운 단위로 나눈 뒤, 사용자가 승인한 계획대로 커밋한다. 커밋 기록은 나중에 누군가 `git log`로 "왜 이 변경이 있었는지"를 따라갈 때 쓰이므로, 메시지는 무엇을 바꿨는지보다 무엇이 달라졌는지가 드러나야 한다.

## 절차

### 1. 저장소 확인

`git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 저장소가 아니면 커밋할 수 없으므로 사용자에게 알리고 멈춘다. 이 프로젝트 루트는 현재 git 저장소가 아닐 수 있다.

### 2. 변경사항 파악

다음을 함께 실행한다.

- `git status --short`: 추적되지 않는 새 파일과 수정·삭제된 파일 목록
- `git diff`: 스테이징되지 않은 변경 내용
- `git diff --staged`: 이미 `git add`된 변경 내용
- `git log --oneline -n 15`: 이 저장소의 기존 메시지 스타일 참고

이미 스테이징된 변경이 있으면, 사용자가 의도적으로 올려 둔 것으로 보고 그 범위를 존중한다. 스테이징 상태를 임의로 비우지 않는다.

### 3. 논리적 단위로 분류

변경을 "한 가지 목적"별로 묶는다. 같은 기능을 위해 함께 바뀌어야 하는 파일(예: 컴포넌트와 그 테스트)은 한 커밋에 둔다. 서로 무관한 변경(예: 린트 설정 정리와 기능 추가)은 나눈다. 단위가 하나뿐이면 하나로 묶는다. 억지로 쪼개지 않는다.

다음 파일은 커밋 대상에서 제외하고 사용자에게 알린다.

- `.env`, 키·토큰·비밀번호가 들어간 파일
- `node_modules/`, 빌드 산출물(`dist/`), 로그
- `hiring-lab/results/`처럼 `.gitignore`에 있어야 할 생성물

`.gitignore`에 없는데 제외해야 할 파일이 보이면, 커밋하지 말고 그 사실만 알려준다.

### 4. 커밋 메시지 작성

형식은 다음과 같다.

```
<type>: <요약>
```

- `type`은 `feat`, `fix`, `refactor`, `chore` 중 하나를 쓴다. 문서는 `docs`, 테스트만 바뀌면 `test`도 쓸 수 있다.
  - `feat`: 사용자가 보는 새 기능이나 동작
  - `fix`: 잘못된 동작 수정
  - `refactor`: 동작은 그대로 두고 구조만 바꿈
  - `chore`: 설정, 의존성, 빌드, 도구 변경
- 요약은 한국어로, 명령형이나 "~함" 어미 대신 간결한 명사형·서술형으로 쓴다. 50자 안팎을 넘기지 않는다. 마침표는 붙이지 않는다.
- 요약에는 "무엇을 바꿨는지"가 드러나야 한다. "수정", "업데이트"처럼 내용이 없는 말은 피한다.
- 변경 이유가 요약만으로 설명되지 않으면 빈 줄 뒤에 본문을 한두 문장으로 덧붙인다.

예시:

```
feat: 생성 실패 시 Gemini 모델 순차 폴백 추가
fix: 미리보기에서 render 호출이 없는 응답을 처리하지 못하던 문제 수정
refactor: 응답 코드펜스 제거 로직을 generator.ts로 분리
chore: 테스트 실행용 jsdom 설정 추가
```

모든 커밋 메시지 끝에는 다음 트레일러를 붙인다. 빈 줄 하나를 두고 쓴다.

```
Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>
```

### 5. 커밋 실행

분류한 계획을 사용자에게 승인받지 않고 바로 실행한다. 실행 전후 결과는 마지막 보고에서 보여준다.

### 6. 단위별 커밋

분류한 단위마다 다음을 수행한다.

1. `git add -- <파일 경로...>`로 그 단위의 파일만 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다. 다른 단위의 변경까지 섞이기 때문이다.
2. 스테이징된 내용이 계획과 맞는지 `git diff --staged --stat`으로 확인한다.
3. HEREDOC으로 메시지를 넘겨 커밋한다.

```bash
git commit -m "$(cat <<'EOF'
feat: 요약

본문(필요할 때만)

Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>
EOF
)"
```

커밋이 실패하면 원인을 확인하고 보고한다. `--no-verify`로 훅을 우회하지 않는다. 훅이 실패하면 원인을 고친 뒤 새 커밋을 만든다. `--amend`는 사용자가 명시적으로 요청할 때만 쓴다.

### 7. 결과 보고

모든 단위를 커밋한 뒤 `git log --oneline -n <커밋 수>`로 결과를 보여준다. 남은 변경(제외한 파일 포함)이 있으면 목록으로 알려준다. push는 하지 않는다. push가 필요하면 사용자가 따로 요청하도록 안내한다.

## 하지 않는 것

- `git push`, `git reset --hard`, `git checkout --`, `git stash`로 사용자의 변경을 버리거나 옮기지 않는다.
- `git add -A`로 무관한 파일을 한꺼번에 올리지 않는다.
- 비밀 정보가 들어 있을 수 있는 파일을 스테이징하지 않는다.
